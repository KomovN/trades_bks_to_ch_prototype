# Надёжность и границы гарантий

## Доставка

Очередь и текущий batch существуют только в памяти одного процесса. Пока процесс
жив, принятый batch не удаляется до успешного INSERT. Неопределённый результат
запроса CH повторяется с теми же строками, включая `received_at`, и может дать дубли.
Падение процесса, SIGKILL, исчерпание shutdown deadline и разрыв WS могут дать потери.
Исторического replay и end-to-end at-least-once нет. Full queue тормозит чтение,
но не гарантирует отсутствие потерь на стороне БКС.

## Writer

- Ограниченная `asyncio.Queue`; запрещено `put_nowait` с молчаливым удалением строк.
- Flush по `BATCH_SIZE` или `FLUSH_INTERVAL_SEC` с первой строки batch; без пустых
  INSERT и busy loop при idle. `time.monotonic()` для интервалов.
- Один writer и один in-flight INSERT. Синхронный клиент выполняется вне event loop.
  Повтор не меняет порядок, raw JSON и timestamp строк.
- `queue.task_done()` вызывается только после успешной записи соответствующей строки,
  а не при её переносе в batch. Нельзя считать `queue.join()` доказательством записи иначе.
- Сетевая ошибка/timeout/временная недоступность CH удерживает batch, закрывает/сбрасывает
  негодный клиент и повторяет с backoff до 10 сек; на shutdown — только до deadline.
- Ошибка схемы, неизвестная таблица, неверный тип/конфигурация или отказ доступа —
  permanent failure. Не превращать любой Exception в бесконечный retry.
- CH connect/I/O имеют конечные timeouts. Отмена `asyncio.to_thread` не прерывает
  поток: deadline и timeouts проектируются совместно и проверяются процессным тестом.

## Reader и auth

Один reader, повторная подписка на каждом reconnect. Exponential backoff 1–60 сек
с jitter и interruptible sleep. Backoff сбрасывается после устойчивой сессии
(не менее 30 сек), а не сразу после handshake: иначе быстро закрываемая сессия зациклится.
WS ping/pong допустим; отсутствие **сделок** не повод разрывать живой WS.

Handshake 401/403 и подтверждённые auth-сообщения/close → invalidate cache и одно
принудительное получение токена; повторный отказ без успешной сессии → permanent auth.
Статический access token не обновляется, его отказ → permanent auth сразу.
HTTP 429/5xx/timeout — временный сбой, Retry-After учитывается в пределах cap.
Token endpoint 400 с `invalid_grant`, 401/403 — permanent auth; прочие 4xx — fatal
configuration/protocol error, без ложного диагноза «refresh token истёк».

Плановая ротация access token вызывает управляемый reconnect и подписку, даже если
старый WS остаётся открыт. Приём не выдумывает истории за время reconnect.

## Supervisor и завершение

Supervisor наблюдает обе worker-задачи. Падение writer останавливает reader;
неожиданное окончание reader завершает приложение. Непредвиденные исключения
не скрываются бесконечным retry. `queue.put`, recv и ожидания могут прерваться остановкой.

Сигнал или fatal error: остановить producer, закрыть WS, согласовать завершение
производителя, затем drain очереди и текущего batch. Нельзя выходить по `queue.empty()`,
пока producer ещё может добавить последнюю строку. Гонка put/stop имеет однозначного
владельца: строка либо учтена принятым элементом очереди, либо учтена как unsaved.

Drain ограничен `SHUTDOWN_TIMEOUT_SEC=30`. Новые retry после deadline не стартуют.
Существующий синхронный запрос имеет суммарный connect + I/O budget не более 15 сек
(внутренние retry драйвера не должны увеличивать его); ожидаемая верхняя граница
выхода процесса 45 сек, Compose `stop_grace_period: 60s`. В T07 необходимо подтвердить
эту границу настоящим процессом; если драйвер её не обеспечивает, изменить реализацию
и согласованные интервалы вместе, а не заявлять ложную гарантию.

Выход 0: обычный сигнал и все принятые строки записаны. Выход 1: fatal auth,
writer/reader failure, истёкший drain deadline или недописанные строки.
При permanent auth после drain действует `AUTH_FAILED_EXIT_DELAY_SEC=600`,
прерываемый сигналом; общий shutdown по сигналу не включает эту задержку.
При dead writer не пытаться бесконечно drain через него.

## Наблюдаемость

Стандартные логи с периодическим summary (по умолчанию 60 сек): received frames,
accepted trades, skipped по фиксированным причинам, source errors, inserted rows,
retry/reconnect, queue size, batch size, unsaved при выходе. Успешный INSERT
подтверждает результат запроса, но число уникальных сделок при неопределённом retry неизвестно.
Не логировать каждую сделку и не выводить raw JSON/секреты/неочищенные exception body.
Логи исключений сторонних клиентов тоже должны проходить проверку утечек.
