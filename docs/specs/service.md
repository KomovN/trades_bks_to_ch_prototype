# Спецификация сервиса

## Цель и scope

Самостоятельный сервис получает **обезличенные рыночные сделки**, а не сделки
брокерского счёта. Он работает 24/7 и сохраняет bronze JSON в существующий ClickHouse.
Начальная подписка — полный список из `quotes_bks_to_ch/subscribe_msg.yaml`:
101 пара ticker/classCode в [YAML](../../subscribe_msg.yaml), `dataType=2` для сделок.
Сервис котировок продолжает работать отдельно.

MVP: Python 3.12, asyncio, `websockets`, `httpx`, `clickhouse-connect`, PyYAML,
python-dotenv; Pydantic допустим для настроек/подписки. Точные совместимые версии
выбираются и фиксируются в T02 по реально прошедшим проверкам.

Вне scope: торговые заявки, аккаунтные сделки, историческая догрузка, торговый
календарь, hot reload, дедупликация, TTL, disk WAL, Kafka, мониторинговый сервер,
изменение существующего quotes-сервиса. Нет требования exactly-once или непрерывной
полноты ленты при обрыве соединения.

## Требования

| ID | Проверяемое поведение |
| --- | --- |
| R01 | Подключение к market-data WS с Bearer и подписка на `dataType=2`; подписка повторяется после каждого reconnect. |
| R02 | В `raw_json` хранится точная полученная строка, включая неизвестные поля и формат чисел. |
| R03 | Строка содержит UTC `received_at` в момент приёма и UTC `event_time` из `dateTime`; missing/invalid timezone не подменяется текущим временем. |
| R04 | Сохраняются только события сделки; ack, ошибка подписки, чужой тип и malformed JSON получают явную классификацию. |
| R05 | Batch ограничен размером и временем; синхронный ClickHouse I/O не блокирует event loop. |
| R06 | Временная недоступность CH удерживает batch и включает backpressure; ошибки схемы/доступа завершают работу с понятной причиной. |
| R07 | Сетевые ошибки WS вызывают retry с ограниченным exponential backoff и jitter; повтор auth не образует частый цикл. |
| R08 | Статический access token приоритетен; refresh token используется для получения и своевременного обновления access token, в том числе при долгой сессии. |
| R09 | Permanent auth останавливает чтение, пытается дописать очередь в пределах deadline, выдерживает interruptible delay и завершает процесс ненулевым кодом. |
| R10 | SIGTERM/SIGINT прерывает recv, ожидание очереди и backoff; принятые строки дописываются до deadline, выход ограничен по времени. |
| R11 | Idle без сообщений нормален: нет фиктивных строк и reconnect по одному лишь отсутствию сделок. |
| R12 | Конфигурация валидируется до сети; секреты не выводятся, env example содержит пустые поля секретов. |
| R13 | Схема ClickHouse в точности соответствует пользовательскому DDL, без TTL и дедупликации; миграция применяется отдельно от ingest. |
| R14 | Отдельный контейнер на существующей VM; локальный CH доступен только для разработки/проверок без подключения к БКС. |
| R15 | Есть проверяемые счётчики/периодические summaries приёма, пропуска, очереди, записи, reconnect и недописанных строк. |
| R16 | Unit/component проверки не требуют сети/секретов; integration проверяет настоящий локальный ClickHouse, live smoke учитывается отдельно. |

## Определение готовности

Каждое требование связано с задачей в [реестре](../../tasks/index.json) и сценарием
в [приёмке](../acceptance.md). Runtime без пройденных сценариев не считается готовым.
Сейчас эти требования являются заданием, а не заявлением о завершённой реализации.
