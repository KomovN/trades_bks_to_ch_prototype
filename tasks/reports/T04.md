# T04 — Авторизация и срок жизни токенов

Статус: выполнено. Owner: `/root/t04_auth`.

## Результат

- Добавлен `AccessTokenProvider` с явными режимами `static`/`refresh`. Static access
  имеет приоритет, не получает deadline и возвращает `False` из `invalidate()`;
  refresh-кэш сбрасывается и обновляется при следующем `get_token()`.
- Refresh-запрос использует фиксированные `client_id=trade-api-read`,
  `grant_type=refresh_token` и token endpoint БКС. HTTP transport и monotonic clock
  внедряются в provider, unit-тесты не используют сеть.
- Срок кэша ограничен минимумом `ACCESS_TOKEN_MAX_AGE_SEC` и валидного
  `expires_in`. Перед deadline применяется safety margin: не более 30 секунд и не
  более 10% выбранного lifetime, чтобы короткий положительный lifetime оставался
  пригодным. Если `expires_in` отсутствует или невалиден, применяется max age и
  пишется предупреждение без response body.
- Reader может читать безопасные `mode`, `is_static`, monotonic `deadline` и `ttl()`.
  Токены, refresh token, payload и headers скрыты из repr provider/response.
- Одновременные `get_token()` сериализованы одним `asyncio.Lock`: один refresh
  обслуживает всех ожидающих consumers.
- Ошибки разделены на `AuthError` для `invalid_grant`/401/403,
  `TemporaryAuthError` для timeout/network/429/5xx и
  `AuthConfigurationError` для прочих 4xx и неверного ответа. Numeric
  `Retry-After` доступен в temporary error и ограничен 60 секундами.
- Исключения HTTP transport преобразуются без exception chaining, поэтому исходный
  текст сторонней ошибки с sentinel secret не попадает в стандартный traceback.

## Ограничения и следующий шаг

- Live token endpoint не вызывался и реальные секреты не использовались. Реальный
  формат ответа, политика refresh-token rotation и одновременное использование
  refresh token несколькими сервисами остаются Q04 для T09.
- Provider сохраняет исходный refresh token из env и не применяет возможный новый
  refresh token из ответа: это согласованный MVP, `.env` не изменяется.
- HTTP-date форма `Retry-After` не интерпретируется; numeric delta поддержан и
  ограничен cap. Планирование ожидания выполняет reader/supervisor, а provider
  только классифицирует ошибку и отдаёт hint.
- T06 должен использовать `mode`/`is_static` для permanent static auth failure и
  `deadline`/`ttl()` для планового reconnect до истечения refresh access token.
