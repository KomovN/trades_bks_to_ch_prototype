# T05 — ClickHouse batch writer

Дата: 2026-10-17. Owner: `/root/t05_writer`.

## Результат

- Реализован `ClickHouseBatchWriter`: один consumer формирует ограниченный batch,
  flush выполняется по `batch_size`, времени от первой строки или после явного
  `producer_done`.
- Синхронные создание клиента, `insert` и `close` вынесены через `asyncio.to_thread`.
  Отмена writer во время INSERT ждёт завершения sync-вызова, ограниченного timeout
  драйвера, поэтому фоновый поток не остаётся бесконтрольно писать после выхода задачи.
- INSERT использует явный порядок колонок
  `received_at, source, ticker, classCode, event_time, raw_json`. Runtime DDL не
  выполняется; `raw_json` и временные значения берутся непосредственно из immutable
  `TradeRawRow`.
- Текущий batch замораживается до первой попытки. При временном или uncertain failure
  клиент закрывается/сбрасывается, backoff растёт до 10 секунд, а следующая попытка
  получает ровно те же строки в том же порядке. Возможные дубли при потере ответа
  тестируются и остаются частью согласованной гарантии.
- `queue.task_done()` вызывается только после успешного возврата INSERT для всего
  batch. Permanent schema/access/configuration failure завершается безопасным
  `PermanentWriteError`, не подтверждает очередь и не включает бесконечный retry.
- `stop_requested`, `producer_done` и общий абсолютный drain deadline разведены.
  Stop только будит writer: завершение возможно лишь после `producer_done` и drain.
  Истечение deadline даёт `DrainDeadlineExceeded` с числом известных unsaved rows.

## Lifecycle API для T07

```python
writer = ClickHouseBatchWriter(queue, client_factory, options)
result = await writer.run(
    producer_done=producer_done_event,
    stop_requested=stop_requested_event,
    drain_deadline=shared_future,
)
```

`drain_deadline` — `asyncio.Future[float]`. Supervisor создаёт его в своём event
loop и ровно один раз устанавливает абсолютное значение `time.monotonic() +
SHUTDOWN_TIMEOUT_SEC` при начале shutdown. Future нельзя отменять. При обычном
окончании producer future может остаться незавершённым. `client_factory` должен
возвращать синхронный clickhouse-connect client; готовая функция
`create_clickhouse_client(settings)` задаёт connect/I/O timeout, `query_retries=0`
и безопасный режим server errors.

Успех возвращает `WriterResult(inserted_rows, insert_attempts, retries)`. Ошибки
`PermanentWriteError` и `DrainDeadlineExceeded` содержат только безопасное сообщение
и `unsaved_rows`; исходное тело ответа CH в exception chain не переносится.

## Оставшиеся риски

- Fake client не доказывает совместимость фактического INSERT, codecs и DateTime64(3)
  с серверной версией ClickHouse; это относится к T08/S15.
- Классификация явно считает transport/timeout/`OperationalError` временными, а
  schema/type/access и неизвестные исключения постоянными. Реальные коды ответов
  конкретной версии CH нужно подтвердить integration-тестом; неизвестная серверная
  ошибка намеренно не превращается в бесконечный retry.
- Верхняя граница завершения зависит от того, что clickhouse-connect соблюдает
  настроенные connect + I/O timeout. T07 должен подтвердить процессную границу,
  T08 — поведение используемой версии драйвера и сервера.
